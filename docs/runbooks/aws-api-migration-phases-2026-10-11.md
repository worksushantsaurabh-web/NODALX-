## Phase 1 — local implementation

- `server/aws-api-http.mjs`: dispatches the current Vercel handlers from Node HTTP, keeps the inbound webhook stream raw, limits JSON to 1 MiB, and applies request timeouts. It binds to loopback through `scripts/start-aws-api.mjs`.
- `scripts/load-aws-api-secret.mjs`: reads one Secrets Manager JSON value through the EC2 instance role and refuses malformed, missing or process-control entries without logging values. `scripts/start-aws-api-from-secrets.mjs` loads it before importing the API.
- `scripts/package-aws-api.mjs`: copies 29 named source/config files to ignored `aws/build/api`. It copies no `.env`, credential cache or `node_modules`; install production dependencies on the host with `npm ci --omit=dev`.
- `aws/api-stack.yaml`: reviewable CloudFormation for a single t4g.small AL2023 ARM host, 20 GiB encrypted gp3, one Elastic IP, HTTPS/HTTP-only API SG, and a private SG-to-SG RDS rule. It uses a separately bootstrapped, tightly scoped instance profile for SSM and staging-secret read access. The template leaves the current public RDS rule untouched. Validated and deployed in Phase 3.
- `aws/nodalx-api.service` and `aws/nodalx-caddy.service` run on the AL2023 host. `NODALX_API_SECRET_ID` is in root-owned `/etc/nodalx-api/bootstrap.env`; it contains only the ARN. The actual JSON secret lives in Secrets Manager. Caddy overwrites `X-Forwarded-For` with the remote peer to prevent client spoofing of the support relay's per-process limiter. Set `SUPPORT_EMAIL_ALLOWED_ORIGINS` to the exact production/Preview origins before routing browser traffic through the external hostname.

Initial staging secret should select `DATA_BACKEND=rds` and include the RDS URL, hosted `SUPABASE_URL` and publishable key. Keep intake, outbound mail, processing, Make and workspace inbound gates disabled until the corresponding staged tests. Copy additional server-only settings from Vercel by name and reviewed value through the AWS console; never print or commit them. The restricted API database role must support only the required app tables and `SET ROLE authenticated/service_role` flows; verify grants in a disposable database before replacing the current `postgres` login.

## Phase 2 — non-root identity gate

The AWS account has root MFA but no IAM users and is not in AWS Organizations (`AWSOrganizationsNotInUseException`). IAM Identity Center **account instances do not provide AWS account permission sets**, so merely enabling one would not create an operator. The owner must bootstrap a non-root IAM console operator with MFA and temporary provisioning permissions, or deliberately establish an AWS Organization with an organization Identity Center instance as a separate identity project. The simpler path for this single account is an IAM console operator. CLI login must return a non-root ARN before deployment. Do not create or paste a long-lived access key. The EC2 instance itself uses the stack's instance role and SSM Session Manager.

On 11 October, the root bootstrap created `arn:aws:iam::560246495281:user/nodalx-operator`. It has only the AWS managed `SignInLocalDevelopmentAccess` policy and the narrow inline `NodalxOperatorSelfMfa` policy in `aws/iam-operator-self-mfa.json`; it has no access key, console login profile, MFA device, or infrastructure permissions. The inline policy follows the allow actions of the [AWS self-managed MFA example](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_policies_examples_iam_mfa-selfmanage.html), scoped to this user. It does not include the example's broad Deny statement because this user has no other resource permissions yet; add an MFA condition to any future provisioning access.

Owner's one-time console sequence: IAM > Users > `nodalx-operator` > Security credentials > Enable console access. Set a new password through the AWS console and require password change at first sign-in. Sign in as that IAM user at `https://560246495281.signin.aws.amazon.com/console/` and enroll an authenticator under Security credentials > MFA. Do not create an access key or paste a password/code in chat. Then run `aws login --profile nodalx-operator` and `aws sts get-caller-identity --profile nodalx-operator`; the ARN must be `arn:aws:iam::560246495281:user/nodalx-operator`. Verify `aws iam list-mfa-devices --user-name nodalx-operator --profile nodalx-console` shows the device before granting any provisioning rights. The first `aws login` may require selecting `us-east-1`.

For the one-time stack/bootstrap work, add only necessary provisioning rights with an MFA condition after the operator login is verified. Do not use the root profile for routine deployment. On 11 October, `aws sts get-caller-identity --profile nodalx-operator` returned `arn:aws:iam::560246495281:user/nodalx-operator`, and IAM `list-mfa-devices` returned one enabled device (FIDO/U2F, enabled 18:23:30 UTC). Phase 2 identity gate is complete. No provisioning policy has been granted; that is the first Phase 3 prerequisite. The root `nodalx-console` CLI login has expired.

## Phase 5 — protected staging verified

On 12 October, complete end-to-end verification of staging APIs was performed against `https://api-staging.nodalx.in`:
- **Boundary & Unauthenticated Probes**: `GET /api/health/live` returned HTTP/2 200 with `x-nodalx-data-source: rds` and Let's Encrypt TLS. Unauthenticated requests to `/api/user/profile`, `/api/workspace/inquiries`, `/api/workspace/usage`, and `/api/feedback` returned 401. Disabled routes (`/api/contact`, `/api/send-email`, `/api/resend-inbound`) returned 503. Invalid JSON returned 400. Non-API paths returned 404. Plain HTTP redirected to HTTPS via 308.
- **Direct Website Intake E2E**: Staged temporary intake source binding in `private.intake_sources` and enabled intake in `nodalx/api/staging` (`RDS_INTAKE_ENABLED=true`, `INTAKE_PROVIDER=rds-direct`, `ALLOW_INTAKE_NETWORK=true`). Restarted `nodalx-api` via SSM.
  1. Initial POST to `/api/contact` returned **201 Created** (`duplicate: false`, `status: 'stored'`) and persisted canonically in `public.inquiries`.
  2. Idempotent replay with same `Idempotency-Key` and identical payload returned **200 OK** (`duplicate: true`, `status: 'stored'`) with zero duplicate rows.
  3. Conflict probe with same `Idempotency-Key` and changed content returned **409 Conflict** (`IDEMPOTENCY_CONFLICT`).
- **Inbound Webhook Verification**: Enabled `WORKSPACE_INBOUND_RECEIVING_ENABLED=true` and `RESEND_WEBHOOK_SECRET`. Probes with missing or forged Svix signatures returned **401 Unauthorized** (`INVALID_WEBHOOK`).
- **Post-Verification Cleanup**: Synthetic inquiry was deleted from `public.inquiries`, temporary source binding was deleted from `private.intake_sources`, verified total inquiries count returned to 0. Restored Secrets Manager staging configuration to safe disabled defaults, and restarted `nodalx-api` via SSM. Staging host is verified and safely idle.

## Phases 6–8 — cutover gates

Phase 6: Update Vercel same-origin rewrites (`vercel.json`) to forward API traffic to the AWS origin. Deploy and verify on Vercel Preview first (`nodalx-staging`), observe live requests, then promote to Production.
Phase 7: Once all live production API traffic flows through the AWS API in the RDS VPC, revoke `0.0.0.0/0` ingress from RDS security group `sg-0333a50a7f3d10246` and set RDS `PubliclyAccessible=false`.
Phase 8: Create dedicated restricted database role for the API, establish backups, CloudWatch alarms, and SSM maintenance procedures.
